# P4-T06-R2A - CANDU source-profile applicability decision

## Outcome

Status: COMPLETE

The bounded applicability decision is complete. The previously audited
`AFA_180_310_type1_dual` HDF5 package is rejected for direct CANDU Core
admission because its embedded case is PWR/assembly data and it does not prove
the frozen P2-T02 node contract. A CANDU-contextual `candu6_iram` package from
the pinned DONJON5 Version5 source tree is selected as the alternate offline
source profile for the next mapping task.

The alternate profile is not a solver-ready Core or golden admission. Its
Gentilly2 coarse geometry and legacy text records provide useful applicability
evidence, but they do not prove explicit `T_g`/`B_g` conductances, `V_i` in
`m^3`, `E_f,i` in `J`, project topology/index mapping, normalization, or mapped
node-level observables. A controlled DONJON5 5.1 execution probe also stopped
during compilation with `IRC=37` and produced no usable reference result.
The remaining technical admission work is therefore isolated as `P4-T06-R2B`.

Effectiveness: PARTIAL

## Assumptions and design choices

- The project-owner redistribution confirmation recorded by R1 is applied to
  the selected external DONJON5 source profile for this offline audit. This is
  a project authorization record, not independent legal advice. No raw source
  bytes are committed or shipped.
- The selected profile is the Version5 `candu6_iram` case, which explicitly
  constructs a Gentilly2 `CAR3D 26 26 12` geometry, uses two groups, and calls
  procedures named `PgeoG2`, `PdevR`, `PdevL`, `Pinires`, `Pmacfix`, and
  `Pfluax`. These facts establish CANDU-contextual source applicability only;
  they do not map the case to the production 380-channel/12-bundle topology.
- The package's `Precf`, `Pow`, burnup values, `IRAM` mode request, and
  `K-EFFECTIVE` assertion are retained as source provenance. None is adopted
  as a project convergence rule, tolerance, normalization, or golden value.
- The legacy `fnat` record names fields including `STRD`, `NUSIGF`, `NFTOT`,
  `CHI`, `NG`, `SIGS`, `SCAT`, `OVERV`, `FLUX-INTG`, `ISOTOPES-EFJ`, and
  `VOLUME`. The record does not carry an explicit project-approved unit binding
  for those fields, so no field is converted into a P2-T02 quantity.
- The relevant P1-T08 digest rows are `S1-R02`, `S1-R03`, `S1-R04`, `S1-R06`,
  `S1-R11`, `S5-R03`, `S5-R04`, `S5-R09`, `S6-R03`, and `S6-R08`. They provide
  CANDU/tool/workflow context and admission limitations only; they are not
  runtime, tolerance, normalization, or golden-data authority.

## Validation commands and results

### T0 - repository format and scope-boundary check

```text
$sdkRoot='<pinned-SDK-root-10.0.302>'
$env:DOTNET_ROOT=$sdkRoot
$env:Path="$sdkRoot;$env:Path"
& .\tools\Check-Format.ps1
$allowedReferenceExtensions=@('.json','.md','.gitkeep')
$unexpectedReferenceFiles=@(Get-ChildItem -LiteralPath 'reference' -Recurse -File |
  Where-Object { $_.Extension.ToLowerInvariant() -notin $allowedReferenceExtensions })
if($unexpectedReferenceFiles.Count -ne 0){
  throw "Unexpected reference file entered the repository: $($unexpectedReferenceFiles.FullName -join ', ')"
}
```

Result: the independent scope-boundary portion passed with
`UnexpectedCount=0`; no raw external payload entered the repository. The
required `Check-Format.ps1` invocation was also attempted after this correction
but could not load because `global.json` requires SDK `10.0.302` with
`rollForward=disable`, while this environment has only `10.0.303` installed.
No format pass is claimed from that invocation. The complete `reference/` tree was
restricted to the approved `.json`, `.md`, and placeholder `.gitkeep` files, so
the check also covers extensionless payloads such as `fnat` and access scripts.
The report and chain were then inspected for host-path leakage.

### T1 - CANDU source-profile audit

```text
Get-Content -LiteralPath '<external-case-root>\candu6_iram.x2m' -Raw
Get-Content -LiteralPath '<external-case-root>\candu6_iram_proc\fnat' -TotalCount 40
Get-ChildItem -LiteralPath '<external-case-root>' -Recurse -File |
  Sort-Object FullName |
  ForEach-Object {
    $hash=Get-FileHash -Algorithm SHA256 -LiteralPath $_.FullName
    '{0} {1} {2}' -f $_.Name,$_.Length,$hash.Hash
  }
```

Result: exit code 0. The case and procedure inventory matched the identities
above for every staged file, including the access script, assertion procedure,
all four extensionless data files, and all six procedure files; the case
explicitly named Gentilly2, `CAR3D 26 26 12`, two groups, and 12 requested
modes. The audit found no explicit mapping from legacy `STRD` or `VOLUME`
records to P2-T02 `T_g`/`B_g`, `V_i`, or `E_f,i`.

```text

docker image inspect 'docker.oecd-nea.org/dragon/5.1@sha256:eb8ddff7d788f563f958ada277a2c8304d2dcf829ef59a35db62438397188d79'
docker run --rm --platform linux/amd64 --network none --pull never --read-only \
  --tmpfs /tmp:rw,exec,nosuid,size=256m --tmpfs /work:rw,exec,nosuid,size=512m \
```

present locally. The controlled package staging completed, including the

compilation with `cle2000_c ... IRC=37` and `DONJON: kernel error (code=666)`.
The emitted result contained no successful completion marker, K-effective
result, or usable reference output. No T6 baseline was claimed.
