## Assumptions and design choices

- The application boundary consumes only the exact due batch returned by
  `CommandQueueV1.TryReleaseDue`; it never applies a command retroactively or
  advances physical/domain state.
- The event identity is the existing command identity, avoiding implicit ID
  generation and making duplicate application fail closed through
  `EventLogV1`.
- All released commands are preflighted against the supplied configuration and
  state-binding authority before any result is returned. Channel owners are
  range-checked against the validated topology, and all current command body
  discriminants are closed-enum checked.
- Existing event-log records are preflighted against the same configuration
  provenance, historical core-state boundary, owner shape/range, body form,
  and application-time boundary before queue release. This prevents a valid
  local queue from being committed into a foreign or malformed log.
- The result owns defensive immutable collections and exposes the new queue/log
  values only after every released event has appended successfully. A failed
  append discards the scratch result and leaves both input objects unchanged.
- A no-due-command boundary is a valid immutable queue advance with an empty
  applied-event list; a missed due boundary is rejected by the existing queue
  contract rather than silently consumed.
